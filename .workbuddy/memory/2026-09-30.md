用户反馈改完后能出声，但仍有概率失败。等待用户回传现场信息（用户 2026-09-30 表示

需要用户确认的两点：
1. 弹窗 `errorMessage` 文案（决定分支）：
   - `未知错误` → `speak()` 返回非 SUCCESS 或引擎 `onError`
   - `朗读操作超时，可能TTS引擎响应过慢` → 等不到 `onDone`，超过动态超时
   - `无法初始化TTS引擎，请检查系统TTS设置` → `onInit` 8s 内未返回 SUCCESS
2. 出问题的安装包是否已包含本次两处改动（尤其 manifest 的 TTS_SERVICE queries 是否生效）。

**已识别、但尚未动手修的残余缺陷**（等现场确认后再改，避免瞎改）：
- `UtteranceProgressListener` 回调在 binder 线程投递，`if (continuation.isActive) resume()`
  是 check-then-act，两个回调并发（如 `onStop` 与 `onDone` 同时到达）会二次 resume →
  `IllegalStateException`。应换成 `AtomicBoolean.compareAndSet` 守卫。
- `onStop` 一律 `resume(true)`：`interrupted=true`（入队后未开始即被 flush）也判成功 →
  表现为「没出声但报成功」。应按 `interrupted` 区分处理。
- `withTimeout` 的计时从进入协程开始，而 `speak()` 是 post 到主线程异步执行的；
  主线程繁忙时会压缩实际可用时长。
- 两个模块（TTS / PlayAudio）都没请求音频焦点，被其他应用占用焦点时可能静音。

**分支解释（重要）**：`TtsEngines.getDefaultEngine()` 内部走 `isEngineInstalled()` →
`queryIntentServices(TTS_SERVICE)`，受 Android 11+ 包可见性限制。若 manifest 缺
`TTS_SERVICE` 的 `<queries>`，`initTts()` 三步全失败 → `dispatchOnInit(ERROR)` →
即上表第三种文案。所以「未重新编译安装」本身就足以解释间歇性的 onInit 失败。

**读码确认的关键机制**（这是本次最大收获，已固化进 MEMORY.md）：
1. `call_workflow` 的 `inputs` 参数**在 UIProvider 里没实现**（只处理 `workflow_id`），
   **无法通过它传参**；实际靠 `executeSubWorkflow` 里 `parentContext.copy()` 的
   **浅拷贝共享 `namedVariables` / `stepOutputs`**：父用「创建变量」写入，子用 `[[名字]]` 读。

   能跑通是因为 `VariableResolver.resolve` **递归解析**，且跨工作流时
   `stepOutputs` 是同一个引用，父工作流递归解析子工作流的 `{{regeo.result}}` 也能命中。
   **可靠但隐式**，是这套子工作流方案的命门。

## 子工作流实际返回「省+市」而非「市+区」的排查（未闭环）

用户反馈跑出来是「省+市」。**推理链**：

- 「省+市」正是 B 站 IP 兜底的输出格式（`江苏`+`常州`）→ 说明坐标是合法的
  （否则前面的 `case` 会拦成「坐标无效」），**高德那一环 `$C` 为空**，落到了兜底。
